# Keyboard Handling

## The Problem

Text inputs near the bottom of a form ended up behind the software keyboard:
the field you were typing into (typically the password field on sign-in) was
invisible, and the screen didn't move at all when the keyboard opened.

## Root Cause

The app is edge-to-edge (`edgeToEdgeEnabled=true`, generated by `expo prebuild`
in `android/gradle.properties`) and targets a modern Android SDK. In
edge-to-edge mode the system no longer resizes **or pans** the app window for
the keyboard, so `android:windowSoftInputMode` (`adjustResize` / `adjustPan`,
set from `softwareKeyboardLayoutMode` in `app.json`) has no effect on the app's
content. The keyboard simply covers the bottom of the window.

That quietly broke the old approach. We used
`react-native-keyboard-aware-scroll-view`'s `KeyboardAwareScrollView`, but on
Android it deliberately does **not** scroll the focused input into view — its
own code assumes "the system would scroll the text input just above the
keyboard" and only adjusts the extra offset. With the system no longer
scrolling, nothing happened at all. iOS was fine, which is why it slipped
through testing. The screen that "worked" only worked because its content was
already taller than the keyboard.

## The Fix

`components/ui/keyboard-aware-scroll-view.tsx` — a small local replacement
that does the whole job in JS/ layout, independent of window resize/pan:

1. On `keyboardDidShow` (iOS: `keyboardWillShow`) it pads the scroll content's
   bottom by the keyboard height, giving the ScrollView somewhere to scroll to.
2. When that padding lands (`onContentSizeChange`), it measures the focused
   input on screen and scrolls by however much it overlaps the keyboard's top
   edge (plus a small gap).
3. On hide it removes the padding.

It defaults to `style={{ flex: 1 }}` and `keyboardShouldPersistTaps="handled"`
so each screen only supplies its content styles.

## Pattern Used Across the App

Every full-screen form uses it:

```tsx
import { KeyboardAwareScrollView } from "@/components/ui/keyboard-aware-scroll-view";

<KeyboardAwareScrollView contentContainerStyle={{ paddingHorizontal: 24, gap: 16 }}>
  {/* form fields */}
</KeyboardAwareScrollView>
```

Screens that vertically centre their content must let the content container
**grow** (`flexGrow`, or the `grow` class in NativeWind) rather than fixing it
to the viewport (`flex-1`): a fixed-height content container gives the
ScrollView no scroll range, so nothing can move when the keyboard opens.

```tsx
<KeyboardAwareScrollView contentContainerClassName="grow justify-center px-6 py-8">
```

For **Modal-based sheets**:
- Plain content → `KeyboardAwareScrollView` (see `components/FeedbackModal.tsx`)
- With `FlatList` → manual `Keyboard.addListener` (see friend picker in
  `app/item/[id].tsx`) — a VirtualizedList can't be nested in a ScrollView
- Pad bottom with `useSafeAreaInsets().bottom` (see
  `components/AvatarPickerModal.tsx`).

`app.json` still sets `android.softwareKeyboardLayoutMode: "pan"`. It now only
matters on Android versions that still honour the flag — input visibility no
longer depends on it, so don't rely on it for new screens.

## What Was Tried (And Ruled Out)

| Approach | Result |
|----------|--------|
| `KeyboardAvoidingView` with `behavior="padding"` | Unreliable; needs a vertical offset that differs per screen, and fights nested scroll views |
| `react-native-keyboard-aware-scroll-view` with `adjustResize` | Scrolled short — inputs stayed hidden |
| `react-native-keyboard-aware-scroll-view` + `softwareKeyboardLayoutMode: "pan"` | Worked until edge-to-edge, then the system stopped panning and the library did nothing on Android |
| `extraScrollHeight` tuning | Never a fix — it only changes the gap above the keyboard |
| **Padding by keyboard height + scroll to focused input** | **Correct solution** |
